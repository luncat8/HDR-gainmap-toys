HDR canvas self-test

One canvas, no scene, no gain maps: it answers “is this browser/display actually showing HDR, and is the transfer function what the demos assume?”. Every patch value below is written straight into the swapchain.

configuring…

Test 1 — transfer function. The four grey cells are CSS colors #404040 #808080 #bfbfbf #ffffff. The canvas patches right under them store 0.25 / 0.5 / 0.75 / 1.0. If each pair reads as one flat block, the canvas is extended sRGB (gamma-encoded, what every shader in this repo encodes for). If the canvas halves look much darker, the canvas is taking linear values and the shaders must not apply the sRGB OETF.
Test 2 — HDR. The five right-hand patches store 1.25 … 4.0, i.e. 1.7× … 25× SDR white. On an HDR display they must be clearly brighter than the 1.0 patch. They stop separating above the display headroom printed below — that is normal clipping, not a bug. Nothing brighter than white at all means the canvas is not on an HDR path: check toneMapping below, the OS HDR switch, and that the window is on the HDR monitor.
Test 3 — the ramp at the bottom of the canvas sweeps 0 → 4; the point where it stops getting brighter is the headroom your display really gives right now.
Test 4 — the plugin. Reload as ?plugin=1 to load hdr-gainmap-plugin.js before the context exists, or flip “swapchain usage” above to the flags it forces. If either changes the picture, the plugin — not the shader math — is what altered the demos.
