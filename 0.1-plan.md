# 0.1 plan — HDR gain map toys

Goal: a static, no-build, `file://`-friendly WebGPU page that

1. opens / drops an image (or synthesizes a test gradient),
2. extends it to HDR with a few intuitive sliders + an editable curve,
3. shows the HDR result on an HDR canvas with a live luminance histogram,
4. writes a real gain-map file (Ultra HDR JPEG) and previews that exact file in `<img>`,
5. verifies the round trip: reads the file back, applies the gain map with the
   standard decoder formula, and shows the reconstructed HDR next to the live one.

## Decisions (after research)

| topic | decision | why |
| --- | --- | --- |
| container | **Ultra HDR JPEG** (SDR JPEG + gain-map JPEG + XMP + MPF) | only gain-map container that can be produced end-to-end in a browser: base/gain-map JPEGs come from `canvas.convertToBlob('image/jpeg')`, metadata is ~1 KB of bytes we write ourselves |
| AVIF gain map | **convert the Ultra HDR JPEG**, never recompute | `avifgainmaputil convert jpg avif` (or `avifenc --qgain-map`) reads the gain map already inside the JPEG and re-encodes it into AVIF, so AVIF == JPEG == authored. Feeding base+alternate to `avifgainmaputil combine` recomputes a *different* gain map and is only for when you have a true HDR alternate (see findings). When the external converter fails (e.g. avifgainmaputil built **without libxml2** — it then cannot read JPEG XMP), `tools/avif_gainmap.py` falls back to a built-in path: split the JPEG itself, `avifenc` both renditions, and repack into the same `tmap` AVIF container libavif writes — the authored gain map still carried over unchanged |
| HDR preview | WebGPU canvas: `format:'rgba16float'`, `colorSpace:'srgb'`, `toneMapping:{mode:'extended'}` | Chrome 129+. Values are **extended-sRGB-encoded**: shader writes `1.055*L^(1/2.4)-0.055` continued above `1.0`; `1.0` = SDR white |
| live view vs decoded view | live `HDR` shows the **full authored** HDR (weight = 1, the canvas tone maps); `saved file` shows the decoder formula at the **real display headroom** | the two were swapped at first: adapting the live view to the display made authoring feel flat and wrong. Authors see the full boost; the headroom slider previews what a viewer on that display gets |
| color working space | sRGB primaries, linear light, `1.0` = SDR white | base JPEG carries no ICC → decoders assume sRGB → gain map is defined in that space. No gamut conversion anywhere, so preview == file |
| tone model | curve `Y_sdr → t` (0..1), `log2 gain = shadowLift + t·(highlightGain − shadowLift)`; `peakNits` sets only the **capacity** | curve range and display capacity are separate quantities and were wrongly conflated. `GainMapMin/Max` = the curve's actual stops range; `HDRCapacityMin/Max` = the display headroom the file is mastered for (usually `max(GainMapMin,0)` .. `log2(peakNits/sdrWhite)`) |
| gain map | single channel, `1/4` of base resolution by default (1, 1/2, 1/4, 1/8 selectable) | spec tip; small file; preview samples the low-res gain texture with the same bilinear filtering a decoder uses, so preview == decode |
| gain math | `log2 gain` is authored directly (no `hdr/sdr` division) | no `log(0)`/offset problems; the curve *is* the gain |
| histogram | low-res `rgba16float` readback of `log2 luma` (source + result), binned on the CPU, drawn on a 2D canvas | a full-res readback per slider tick is heavy; 192×108 samples is plenty for a distribution and stays snappy |
| metadata | full `hdrgm:` block in **both** images + `Container:Directory` in the primary | matches Google reference samples (checked byte-wise against a Pixel Ultra HDR file) and keeps Chrome (MPF route) and Google Photos (GContainer route) happy |
| verification | in-page decode + `exiftool` on files produced by `tests/node/ultrahdr.test.js`; `tools/avif_gainmap.py` assembles the same container byte-for-byte (checked against the JS builder) | no browser in the sandbox: the container is verified with an independent parser, the math with a round-trip |

## File layout of a produced Ultra HDR JPEG

```
[primary JPEG]  SOI
                APP1 XMP  (hdrgm params + Container:Directory, Item:Length=<gain map size>)
                APP2 MPF  (86 bytes of data, CIPA DC-007)
                ... original JPEG segments (JFIF/DQT/SOF/DHT/SOS) ...
                EOI
[gain map JPEG] SOI
                APP1 XMP  (same hdrgm params)
                ... JPEG (grayscale when the browser emits grayscale) ...
                EOI
```

MPF APP2 (little-endian TIFF, verified against a Pixel sample):

```
FF E2 00 58 "MPF\0"  II 2A00 <ifd=8>
IFD: count=3
  0xB000 MPFVersion     type 7 count 4  "0100"
  0xB001 NumberOfImages type 4 count 1  2
  0xB002 MPImageList    type 7 count 32 offset 50 (from TIFF header)
next IFD = 0
entry 0: attr 0x00030000 (primary)  size=<primary bytes>  offset=0        dep 0,0
entry 1: attr 0x00000000            size=<gainmap bytes>  offset=<gap>    dep 0,0
```

* Offsets are **relative to the TIFF header**, i.e. to the byte right after `MPF\0`
  (confirmed: Pixel sample entry 1 = 2599690, TIFF header at 84458, gain-map SOI at 2684148).
* Images are tightly packed: assemble first, then patch the two offsets with the
  real gap (see `ultrahdr.js` / `tools/avif_gainmap.py`, which mirror each other).
* `Item:Length` in `Container:Directory` = byte length of the gain-map JPEG.

## Gain map math

Authoring (browser, per pixel, linear light, `Y` = Rec.709 luminance):

```
t          = curve(Ysdr)                     // 0..1, editable LUT
log2gain   = shadowLift + t*(highlightGain - shadowLift)
hdr        = sdr_linear * exp2(log2gain)
recovery   = t
encoded    = round(recovery*255)
```

* `shadowLift` (curve bottom) and `highlightGain` (curve top) are the gain map's
  stops range; the quick tone sliders set them and `threshold` reshapes the ramp.
* `peakNits` and `sdrWhite` set `HDRCapacityMax = log2(peakNits/sdrWhite)` only;
  `highlightGain` is capped at that. Lower `highlightGain` than capacity is fine:
  the file then simply never uses the extra headroom, and the metadata says so.

Metadata: `GainMapMin=rangeMin`, `GainMapMax=rangeMax` (from the LUT's actual
min/max), `HDRCapacityMin=max(rangeMin,0)`, `HDRCapacityMax=log2(peakNits/sdrWhite)`,
`OffsetSDR=OffsetHDR=0`, `Version=1.0`, no `Gamma` (=1) and no
`BaseRenditionIsHDR` (=False).

Decoding (Ultra HDR v1.0, implemented in `ultrahdr.js` for the in-page check):

```
recovery      = encoded/255
log_recovery  = recovery^(1/gamma)
log_boost     = GainMapMin*(1-log_recovery) + GainMapMax*log_recovery
weight        = clamp((log2(display_boost) - HDRCapacityMin)/(HDRCapacityMax - HDRCapacityMin), 0, 1)
hdr           = (sdr + offset_sdr) * exp2(log_boost*weight) - offset_hdr
```

Displayed boost is `exp2(log_boost*weight)`: the authored boost is only reached
when the display headroom `>= 2^HDRCapacityMax`. The **live** view renders with
`weight = 1` (the canvas tone maps); the **saved file** view renders with the
real headroom (`screen.highDynamicRangeHeadroom`, else the "headroom" slider).

## Modules

| file | contents |
| --- | --- |
| `index.html` | markup: drop zone, source/view canvases + histogram, controls, saved-file `<img>` |
| `style.css` | dark, two-column layout, no framework |
| `src/ui.js` | slider/checkbox/button builders from flat tables, status line |
| `src/gpu.js` | WebGPU device, canvas configure (HDR detection), texture/buffer helpers, readback |
| `src/shaders.js` | WGSL: `gain` (curve → recovery), `hdr` (sdr+gain → linear HDR), `present` (HDR → extended sRGB canvas), `decode` path reuses `hdr`, `hist` (log2 luma of two textures) |
| `src/curve.js` | canvas curve editor: draggable control points, monotone spline → 64-entry LUT texture; parametric `rampPoints(threshold)` for the quick tone sliders |
| `src/patterns.js` | synthesized test sources (ramp, sun+sky, steps, checker) as `ImageBitmap` |
| `src/ultrahdr.js` | JPEG segment walk, XMP build/parse, MPF build/parse, `buildUltraHDR`, `parseUltraHDR`, `applyGainMap` (CPU, for checks) |
| `src/app.js` | state, passes, histogram, save/export, preview, round-trip verification |
| `tests/node/ultrahdr.test.js` | node smoke test: builds a file from two JPEGs, asserts structure; writes `out/*.jpg` for `exiftool` |
| `tools/avif_gainmap.py` | terminal AVIF path: assembles an Ultra HDR JPEG (byte-identical to `ultrahdr.js`) or takes one, then `avifgainmaputil convert` (or `avifenc --qgain-map`) to a gain-map AVIF; on external failure falls back to its own Ultra HDR splitter + `avifenc` + `tmap` AVIF container writer (no libxml2 needed) |
| `tests/python/avif_gainmap.test.py` | the python path: Ultra HDR parse/build round trip, hdrgm→`tmap` metadata mapping, AVIF container merge (needs `pillow` + `pillow-avif-plugin` for real AV1) |

All `src/*.js` are classic scripts: they attach to `globalThis` and guard
`module.exports` so the same code runs in node tests. No fetch of WGSL, no
modules → works from `file://`.

## Controls

* source: drop / open / synthesized pattern (ramp, sky, steps, checker)
* tone: shadow lift (stops), highlight gain (stops, capped by peak), highlight
  threshold (Y where the ramp starts) — these write the curve
* HDR range: peak nits, SDR white nits, gain-map scale
* curve editor: `Y_sdr → boost`, presets (linear, highlights, shadows, s-curve, flat)
* preview: view (HDR / SDR base / gain map / saved file), exposure (stops),
  display headroom (default = detected), histogram on/off + log/linear
* histogram: live log2-luminance distribution of source vs result, with markers
  at SDR white, display headroom and mastered peak
* actions: save Ultra HDR JPEG, export base+gain-map JPEG pair + `metadata.json`
  (terminal AVIF path), report line with sizes/offsets/metadata and round-trip error

## Verification plan

1. `node tests/node/ultrahdr.test.js` → assemble an Ultra HDR file from two real
   JPEGs (produced by Pillow) and dump its structure.
2. `exiftool -G1 -n -xmp -b out/test.jpg` → independent check that XMP `hdrgm:*`
   and MPF `MPImage1/2` parse, sizes/offsets point at the real SOI offsets.
3. Compare the dumped structure with a real Pixel Ultra HDR sample: same MPF
   length (86 data bytes), same attribute words, same XMP fields.
4. `tools/avif_gainmap.py base.jpg gainmap.jpg meta.json` must assemble a file
   byte-identical to the JS builder's (checked in the sandbox with `cmp`).
5. In the browser: save → the page decodes its own file and reports the max
   difference (in stops) against the live HDR render, plus the `<img>` preview
   must look identical to the SDR base.
6. Manual, on the user's HDR display: file opens in Chrome/Photos and highlights
   are brighter than the base; the AVIF produced by the terminal step shows the
   same boost (use `avifgainmaputil printmetadata out.avif`).

## Run

```
open index.html            # file:// works, no server needed
node tests/node/ultrahdr.test.js    # container + math, writes tests/out/*.jpg
node tests/node/app.smoke.js        # app wiring against a stubbed DOM/WebGPU
python3 tools/avif_gainmap.py photo_ultrahdr.jpg --dry-run          # AVIF convert
python3 tools/avif_gainmap.py base.jpg gainmap.jpg meta.json -o out.avif
python3 tests/python/avif_gainmap.test.py   # python tests (AV1 parts need pillow-avif-plugin)
```

Needs Chrome 151+ and, for the HDR preview itself, an HDR display (without one
the canvas shows the SDR rendition and the "SDR base" view looks the same).

## Out of scope (documented in findings-pitfalls-skills.md)

* AVIF gain map *from scratch* in the browser (no AV1 encoder, no container writer).
* per-channel (colour) gain maps — single channel keeps metadata single valued.
* HEIF/JXL, HDR10/PQ metadata, EXIF/ICC embedding.
