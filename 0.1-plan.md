# 0.1 plan — HDR gain map toys

Goal: a static, no-build, `file://`-friendly WebGPU page that

1. opens / drops an image (or synthesizes a test gradient),
2. extends it to HDR with sliders + an editable curve,
3. shows the HDR result on an HDR canvas,
4. writes a real gain-map file (Ultra HDR JPEG) and previews that exact file in `<img>`,
5. verifies the round trip: reads the file back, applies the gain map with the
   standard decoder formula, and shows the reconstructed HDR next to the live one.

## Decisions (after research)

| topic | decision | why |
| --- | --- | --- |
| container | **Ultra HDR JPEG** (SDR JPEG + gain-map JPEG + XMP + MPF) | only gain-map container that can be produced end-to-end in a browser: base/gain-map JPEGs come from `canvas.convertToBlob('image/jpeg')`, metadata is ~1 KB of bytes we write ourselves |
| AVIF gain map | **not produced in browser** | needs an AV1 encoder plus an AVIF container with an `altr` item; nothing in the browser exposes either. Terminal fallback (`tools/avif_gainmap.py`, requires `avifgainmaputil`) is exported to, not implemented in, the browser |
| HDR preview | WebGPU canvas: `format:'rgba16float'`, `colorSpace:'srgb'`, `toneMapping:{mode:'extended'}` | Chrome 129+. Values are **extended-sRGB-encoded**: shader writes `1.055*L^(1/2.4)-0.055` continued above `1.0`; `1.0` = SDR white |
| color working space | sRGB primaries, linear light, `1.0` = SDR white | base JPEG carries no ICC → decoders assume sRGB → gain map is defined in that space. No gamut conversion anywhere, so preview == file |
| gain map | single channel, `1/4` of base resolution by default (1, 1/2, 1/4, 1/8 selectable) | spec tip; small file; preview samples the low-res gain texture with the same bilinear filtering a decoder uses, so preview == decode |
| gain math | `log2 gain` is authored directly (no `hdr/sdr` division), `GainMapMin..GainMapMax` = authored range | no `log(0)`/offset problems; the curve *is* the gain |
| metadata | full `hdrgm:` block in **both** images + `Container:Directory` in the primary | matches Google reference samples (checked byte-wise against a Pixel Ultra HDR file) and keeps Chrome (MPF route) and Google Photos (GContainer route) happy |
| verification | in-page decode + `exiftool` on files produced by `tests/node/ultrahdr.test.js` | no browser in the sandbox: the container is verified with an independent parser, the math with a round-trip |

## File layout of a produced Ultra HDR JPEG

```
[primary JPEG]  SOI
                APP1 XMP  (hdrgm params + Container:Directory, Item:Length=<gain map size>)
                APP2 MPF  (86 bytes of data, CIPA DC-007)
                ... original JPEG segments (JFIF/DQT/SOF/DHT/SOS) ...
                EOI
[gain map JPEG] SOI
                APP1 XMP  (same hdrgm params)
                ... JPEG (grayscale when the browser emits grayscale) ...
                EOI
```

MPF APP2 (little-endian TIFF, verified against a Pixel sample):

```
FF E2 00 58 "MPF\0"  II 2A00 <ifd=8>
IFD: count=3
  0xB000 MPFVersion     type 7 count 4  "0100"
  0xB001 NumberOfImages type 4 count 1  2
  0xB002 MPImageList    type 7 count 32 offset 50 (from TIFF header)
next IFD = 0
entry 0: attr 0x00030000 (primary)  size=<primary bytes>  offset=0        dep 0,0
entry 1: attr 0x00000000            size=<gainmap bytes>  offset=<gap>    dep 0,0
```

* Offsets are **relative to the TIFF header**, i.e. to the byte right after `MPF\0`
  (confirmed: Pixel sample entry 1 = 2599690, TIFF header at 84458, gain-map SOI at 2684148).
* Images are tightly packed: `offset1 = primary_size - (xmp_len + 10)` with
  `xmp_len` = length of the APP1 segment including its marker; simpler: assemble first,
  then patch the two offsets with the real gap (see `ultrahdr.js`).
* `Item:Length` in `Container:Directory` = byte length of the gain-map JPEG.

## Gain map math

Authoring (browser, per pixel, linear light, `Y` = Rec.709 luminance):

```
t          = curve(Ysdr)                     // 0..1, from the editable LUT
log2gain   = minStops + t*(maxStops-minStops)
hdr        = sdr_linear * exp2(log2gain)
recovery   = t                               // = (log2gain - minStops)/(maxStops-minStops)
encoded    = round(recovery*255)
```

Metadata: `GainMapMin=minStops`, `GainMapMax=maxStops`,
`HDRCapacityMin=max(minStops,0)`, `HDRCapacityMax=maxStops`,
`OffsetSDR=OffsetHDR=0`, `Version=1.0`, no `Gamma` (=1) and no
`BaseRenditionIsHDR` (=False). `maxStops = log2(peakNits/sdrWhiteNits)`.

Decoding (Ultra HDR v1.0, implemented in `ultrahdr.js` for the in-page check):

```
recovery      = encoded/255
log_recovery  = recovery^(1/gamma)
log_boost     = min*(1-log_recovery) + max*log_recovery
weight        = clamp((log2(display_boost) - capacity_min)/(capacity_max - capacity_min), 0, 1)
hdr           = (sdr + offset_sdr) * exp2(log_boost*weight) - offset_hdr
```

Displayed boost is therefore `exp2(log_boost*weight)`, i.e. the authored boost is
only reached when the display headroom `>= 2^HDRCapacityMax`. The preview uses the
real headroom (`screen.highDynamicRangeHeadroom`, else the "headroom" slider) so
the canvas matches a real viewer.

## Modules

| file | contents |
| --- | --- |
| `index.html` | markup: drop zone, source/view canvases, controls, saved-file `<img>` |
| `style.css` | dark, two-column layout, no framework |
| `src/ui.js` | slider/label/button builders from flat tables, status line |
| `src/gpu.js` | WebGPU device, canvas configure (HDR detection), texture/buffer helpers, readback |
| `src/shaders.js` | WGSL: `gain` (curve → recovery), `hdr` (sdr+gain → linear HDR), `present` (HDR → extended sRGB canvas), `decode` (base+gain map → HDR, the verification path) |
| `src/curve.js` | canvas curve editor: draggable control points, monotone spline → 256-entry LUT texture |
| `src/patterns.js` | synthesized test sources (ramp, sun+sky, steps, checker) as `ImageBitmap` |
| `src/ultrahdr.js` | JPEG segment walk, XMP build/parse, MPF build/parse, `buildUltraHDR`, `parseUltraHDR`, `applyGainMap` (CPU, for checks) |
| `src/app.js` | state, passes, save/export, preview, round-trip verification |
| `tests/node/ultrahdr.test.js` | node smoke test: builds a file from two JPEGs, asserts structure; writes `out/*.jpg` for `exiftool` |
| `tools/avif_gainmap.py` | terminal fallback: `base.png` + `hdr.png` → gain-map AVIF via `avifgainmaputil` (best effort, binary not present here) |

All `src/*.js` are classic scripts: they attach to `globalThis` and guard
`module.exports` so the same code runs in node tests. No fetch of WGSL, no
modules → works from `file://`.

## Controls

* source: drop / open / synthesized pattern (ramp, sun, steps, checker)
* HDR: peak nits, SDR white nits, floor gain (stops), gain-map scale,
  JPEG quality (base, gain map)
* curve editor: `Y_sdr → boost`, presets (linear, highlights-only, shadows+highs, S-curve)
* preview: exposure (stops), view (live HDR / SDR base / gain map / saved file),
  display headroom (default = detected), clamp-to-SDR compare
* actions: save Ultra HDR JPEG, export base+gain-map PNG pair + `metadata.json`
  (terminal AVIF path), report line with sizes/offsets/metadata and round-trip error

## Verification plan

1. `node tests/node/ultrahdr.test.js` → assemble an Ultra HDR file from two real
   JPEGs (produced by Pillow) and dump its structure.
2. `exiftool -G1 -n -xmp -b out/test.jpg` → independent check that XMP `hdrgm:*`
   and MPF `MPImage1/2` parse, sizes/offsets point at the real SOI offsets.
3. Compare the dumped structure with a real Pixel Ultra HDR sample: same MPF
   length (86 data bytes), same attribute words, same XMP fields.
4. In the browser: save → the page decodes its own file and reports the max
   difference (in stops) against the live HDR render, plus the `<img>` preview
   must look identical to the SDR base.
5. Manual, on the user's HDR display: file opens in Chrome/Photos and highlights
   are brighter than the base.

## Run

```
open index.html            # file:// works, no server needed
node tests/node/ultrahdr.test.js    # container + math, writes tests/out/*.jpg
node tests/node/app.smoke.js        # app wiring against a stubbed DOM/WebGPU
python3 tools/avif_gainmap.py base.png gainmap.png gainmap.json --dry-run
```

Needs Chrome 151+ and, for the HDR preview itself, an HDR display (without one
the canvas shows the SDR rendition and the "clamped" view looks the same).

## Out of scope (documented in findings-pitfalls-skills.md)

* AVIF gain map in the browser (no AV1 encoder, no container writer).
* per-channel (colour) gain maps — single channel keeps metadata single valued.
* HEIF/JXL, HDR10/PQ metadata, EXIF/ICC embedding.
